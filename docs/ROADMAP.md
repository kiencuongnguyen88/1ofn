# 1ofN Roadmap

This is a **living capability roadmap**, not a promise to build everything listed here.

The first public release should remain:

- easy to understand;
- easy to remember;
- cheap to use;
- useful without software;
- small enough to maintain well.

Growth should be pulled by real use.

## Rhythm 1 — always allowed to grow

Low-cost surfaces close to the core:

- worked cases;
- failure and reversal cases;
- evaluation cases;
- examples of `MERGE`, `PARK`, and `BLOCKED`;
- non-activation examples;
- localization;
- lineage;
- clearer execution guidance.

These improve understanding and evidence without changing the method spine.

## Rhythm 2 — grow when repeated use creates a need

Open capability work only when repeated cases expose a real weakness.

Examples:

- recurring evidence conflicts;
- repeated nested decisions;
- dependency handling that current runs do poorly;
- traceability becoming expensive;
- repeated difficulty deciding when to stop.

Possible response:

- deepen an existing stage;
- strengthen evals;
- improve persistence/trace;
- add or replace a tool;
- improve recursive execution while preserving the same five-stage spine.

Do not add a new top-level method stage unless repeated real cases prove the existing five cannot absorb a material capability without semantic distortion.

## Rhythm 3 — grow only when an ecosystem exists

Reopen larger infrastructure only when real adoption creates the need.

Signals may include:

- third-party implementations;
- contributors;
- integrations;
- compatibility claims;
- canonical version disputes;
- repeated software/tooling demand.

Possible future surfaces:

- reference implementation;
- compatibility tests;
- contribution governance;
- brand/naming policy;
- formal interoperability work.

These are not v0.1 requirements.

## Permanent direction

`1ofN` should become stronger through:

- practice;
- evidence;
- evaluation;
- learning;
- better tools.

It should not become larger merely because more architecture is imaginable.
