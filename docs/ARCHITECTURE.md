# 1ofN Architecture

This document explains how `1ofN` can grow for a long time without becoming a different method.

The public five-stage method remains:

`FRAME → EXPAND → CHALLENGE → DISTILL → DECIDE`

The architecture around it has three layers with three different laws of change.

## 1. Constitution — do not drift

Question:

> What must remain true for this still to be 1ofN?

Roles:

- **WHAT** — specialist identity;
- **PROBLEM** — the persistent selection problem;
- **WHO / WHEN** — activation boundary;
- **HOW** — five-stage mechanism, stable verdicts, removal test, bounded backloops, stop/reversal behavior.

A normal version upgrade should not change these four.

If a change materially breaks one of them, treat it as an identity-breaking change and review whether the result is a successor or a different method.

## 2. Capability — improve through practice

Question:

> What can the same 1ofN become better at over time?

Roles:

- **REASONING DEPTH** — stronger processing inside the fixed five stages;
- **PRACTICE / REALITY EXPERIENCE** — accumulated real cases, failures, reversals, and later outcomes;
- **EVALUATION / PROOF** — evidence that a newer execution is actually better;
- **LEARNING / EVOLUTION** — safely convert proven lessons into versioned improvements.

A stronger 1ofN does not need more top-level stages. It should first become better inside the existing ones.

## 3. Tools — replace when better

Question:

> What replaceable instruments can help perform the work?

Roles:

- **ACQUIRE / ACCESS** — obtain relevant source, data, files, search results, expert input, or future inputs;
- **PROCESS / REASON** — models, solvers, graphs, simulation, clustering, or future reasoning engines;
- **VERIFY / CHALLENGE** — contradiction checks, provenance, adversarial review, formal checks, scenario stress;
- **PERSIST / TRACE** — decision packets, evidence trace, state, history, child/parent links, audit artifacts;
- **ORCHESTRATE / ROUTE** — bind tools to fixed roles, coordinate child runs, route outputs, and stop tools from redefining the method.

Tools are vehicles, not semantic owners.

A better tool may strengthen a role. It does not get to redefine `KEEP`, skip `DISTILL`, remove the removal test, or turn a provisional result into unquestionable truth.

## Authority direction

```text
CONSTITUTION
     ↓
CAPABILITY
     ↓
TOOLS
```

Tools may strengthen capability. Capability may deepen execution of the constitution. Authority does not flow upward by default.

## Governance

A separate governance layer is intentionally **not active yet**.

Current governance needs are absorbed by:

- the constitutional identity-change rule;
- Learning / Evolution;
- eval/change gates;
- version lineage.

Reopen a separate governance decision only when real ecosystem needs appear, such as multiple independent implementations, contributor authority conflicts, compatibility disputes, or canonical release ownership.

## Compatibility with future growth

This architecture does not require predicting future technology.

If a future tool can make one of the fixed roles materially better while preserving the constitutional contract, it can be adopted.

That is the point: the method can remain recognizable while its execution capability changes dramatically.
